## 2. Запуск

Бэкенд — из корня репозитория: `docker compose up --build -d` (API на :8000, см. `backend/README.md`).
Фронтенд — `frontend/README.md`: `npm ci && npm run dev`, http://localhost:5173, Vite проксирует `/api` на :8000
(другой адрес — `API_TARGET`). Демо-данные возвращает `POST /api/demo/reset` (кнопка в очереди аналитика).

## 3. Как фронт ходит в API

Все запросы — через `src/api/client.js` → `src/api/http.js`. Локальных моков и копий справочников нет.

- **Авторизация.** `POST /api/auth/login` → `{accessToken, user, expiresIn}` хранится в `sessionStorage`
  (своя сессия у каждой вкладки: клиент и аналитик открываются рядом). Заголовок `Authorization: Bearer …`.
  Выход — `POST /api/auth/logout` и удаление токена.
- **Ошибки** `{error: {code, message, fields}}`:

  | Ответ | Реакция |
  |---|---|
  | 401 | токен удаляется, переход на `/login` |
  | 403 | «Недостаточно прав» |
  | 404 | экран «Не найдено» с кнопкой к списку заявок / очереди |
  | 409 (любой код) | показываем `message` и перечитываем данные экрана; в мастере `not_draft` — переход на страницу статуса |
  | 422 | `fields[].field` → ошибка у поля формы; `invalid_code` — текстом у поля кода |
  | 5xx, обрыв сети | «Сервис временно недоступен, попробуйте позже», уже показанные данные не пропадают |

- **Перечитывание.** После любого успешного изменяющего запроса и после 409 все загруженные данные на экране
  запрашиваются заново (событие `smart-credit-change`).
- **Опрос карточки заявки** (`useApplication`) — интервал по статусу, только на видимой вкладке, останавливается при уходе со страницы:

  | Статус | Интервал |
  |---|---|
  | `submitted`, `validation`, `enrichment`, `scoring` | 2,5 с первую минуту в статусе, затем 10 с |
  | `manual_review`, `docs_requested`, `approved`, `counter_offer` | 15 с |
  | `draft`, `signing`, `issued`, `rejected`, `declined_by_client` | не опрашивается |

  Списки «Мои заявки» и очередь аналитика — раз в 15 с.
- **Отправка заявки** — `POST /api/applications/{id}/submit` с заголовком `Idempotency-Key`: один ключ на открытие
  мастера, повторное нажатие не создаёт дубль.
- **Справочники** (`GET /api/dictionaries`) запрашиваются один раз на вкладку; при ошибке — повторно на следующем экране.
- Кнопки действий блокируются на время запроса.

## 5. Статусы

Подписи — `src/config/statuses.js`, у всех 13 статусов: «Черновик», «Заявка подана», «Проверяем анкету»,
«Запрашиваем сведения», «Оцениваем заявку», «На проверке у специалиста», «Нужна информация», «Одобрено»,
«Контрпредложение», «Отказ», «Подписание договора», «Кредит выдан», «Клиент отказался».

Таймлайн строится из `history`: шаги — события `kind: status_changed`; `checks_refreshed` и любой другой `kind` —
отметка с `note` внутри текущего шага, статус не дублируется. Ещё не пройденные шаги основного пути показываются серыми.

## 6. Проверки (`checks`)

- Порядок вывода — по `source`: банк, ЕГРЮЛ / ЕГРИП, НБКИ, «Прозрачный бизнес».
- `status`: `ok` «В порядке», `warning` «Есть замечания», `fail` «Не пройдена»,
  `unavailable` — нейтральный бейдж «Источник временно недоступен» (у клиента и у аналитика).
- **Клиент** видит название, `summary` и статус; внутренних полей банка не использует.
- **Аналитик** дополнительно видит время данных (`fetchedAt`) и блок «Подробнее» с ключевыми `details`:
  - банк — поступления в месяц, изменение за 12 месяцев, срок оборотов;
  - ЕГРЮЛ / ЕГРИП — статус, дата регистрации и срок работы, руководитель, ОГРН, ОКВЭД, адрес;
  - НБКИ — рейтинг бюро, платежи по кредитам, остаток долга, текущая просрочка, просрочки за 24 месяца, длина истории, запросы за 30 дней;
  - «Прозрачный бизнес» — найденные признаки риска (массовый адрес или руководитель, дисквалифицированные лица,
    недостоверные сведения, налоговый долг, несданная отчётность), налоговый режим, сотрудники, выручка и прибыль;
  - `unavailable` — причина подписью из `dictionaries.unavailableReasons` и код ответа источника.

  Схема `details` выбирается по `source` и `status`; `details: null` — блок не показывается, пустые поля пропускаются.
- **«Обновить данные из источников»** — только в `enrichment`, `scoring`, `manual_review`, `docs_requested`.
  На время запроса (до ~10 с) кнопка заблокирована и показан индикатор; ответ заменяет карточку.

## 7. Решение аналитика

Форма — только в `manual_review` и `docs_requested`. Действие выбирается кнопкой:
`approve` (на запрошенных условиях), `counter_offer` (сумма меньше запрошенной, подсказка — `systemRecommendation.amount`),
`request_docs` (пункты из `dictionaries.infoItems`), `reject` (причина из `dictionaries.rejectReasons`).
Комментарий для клиента обязателен для всех действий, кроме `approve`. Те же правила проверяются на фронте до отправки,
ошибки сервера из `fields` показываются у полей.

## 8. Ограничения этапа 3

- Конвейер не запущен: отправленная заявка остаётся в `submitted`, после ответа на запрос информации — в `validation`.
  Опрос по статусу уже работает и покажет движение заявки на этапе 4 без изменений на фронте.
- Скоринг, рекомендации, объяснения и подбор продукта считает бэкенд; на фронте правил нет.
