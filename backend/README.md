# Бэкенд

FastAPI-приложение: API личного кабинета, кредитный конвейер, скоринг.

> **Этап 3.** Данные хранятся в PostgreSQL. Подключены внешние источники через симулятор `mocks/`:
> специалист может запросить по заявке данные ЕГРЮЛ/ЕГРИП, НБКИ и «Прозрачного бизнеса».
> Конвейер обработки ещё не запущен: отправленная заявка остаётся в статусе `submitted` (появится на этапе 4).

## Запуск в Docker

Из корня репозитория:

```bash
docker compose up --build -d     # первый запуск или после изменений в коде
docker compose ps                # api, mocks — healthy; migrate — Exited (0)
docker compose logs migrate      # что сделала подготовка базы
```

Swagger: http://localhost:8000/api/docs, симулятор источников: http://localhost:8001/docs

Порядок старта:

```
postgres (healthy) → migrate: alembic upgrade head + сиды (завершается) ─┐
mocks (запущен) ─────────────────────────────────────────────────────────┴→ api: uvicorn (healthy)
```

`migrate` — разовая задача: она завершается после подготовки базы, и это нормально. Перезапуск безопасен:
применённые миграции пропускаются, справочники обновляются, созданные заявки не удаляются.

Сбросить данные:

| Что нужно | Команда |
|---|---|
| вернуть демо-заявки в исходное состояние | `POST /api/demo/reset` (кнопка в Swagger) |
| пересоздать базу полностью | `docker compose down -v && docker compose up --build -d` |

`-v` удаляет том `pgdata` с данными базы — используйте осознанно.

## Локальный запуск без Docker

Нужен [uv](https://docs.astral.sh/uv/) и Python 3.12 (`uv python install 3.12`). База — из Docker:

```bash
docker compose up -d postgres mocks            # из корня: база (127.0.0.1:5432) и симулятор (127.0.0.1:8001)

cd backend
uv sync                                        # зависимости из uv.lock
uv run alembic upgrade head                    # схема базы
uv run python -m app.db.seed                   # справочники и демо-заявки (--reset — пересоздать заявки)
uv run uvicorn app.main:app --reload           # http://localhost:8000/api/docs
```

Не запускайте одновременно локальный uvicorn и контейнер `api`: оба занимают порт 8000
(остановить контейнер — `docker compose stop api`).

## Тесты

```bash
docker compose up -d postgres    # из корня
cd backend
uv run pytest                    # все тесты
uv run pytest tests/test_state_machine.py tests/test_requisites.py tests/test_integrations.py   # без базы
```

- Тесты используют **отдельную базу `credit_test`**: она создаётся автоматически, миграции применяются
  один раз за запуск, демо-данные пересоздаются перед каждым тестом. Рабочая база `credit` не затрагивается.
- Другой адрес — переменная `TEST_DATABASE_URL`; имя базы обязано оканчиваться на `_test` (защита от запуска на рабочей базе).
- Запущенный симулятор **не нужен**: тесты поднимают код из `mocks/simulator` прямо в процессе, без сети и задержек.
  Поэтому адаптеры проверяются против настоящих ответов симулятора, а не против придуманных.

| Файл | Что проверяет |
|---|---|
| `test_api_contract.py` | контракт API: коды ответов, формат ошибок, проекции, сквозные сценарии |
| `test_state_machine.py` | автомат статусов: разрешённые и запрещённые переходы, полнота графа, история демо-заявок |
| `test_database.py` | миграции совпадают с моделями, идемпотентность сидов, CHECK-ограничения, оптимистичная блокировка |
| `test_requisites.py` | контрольные суммы ИНН, ОГРН и расчётных счетов в синтетических данных |
| `test_integrations.py` | адаптеры источников: повторы, таймауты, ошибки 4xx/5xx, неожиданный формат, ответы симулятора |
| `test_enrichment.py` | правила оценки источников, согласованность демо-данных с симулятором, обновление проверок специалистом |
| `test_openapi.py` | `docs/api/openapi.json` совпадает с кодом; все коды 409 описаны |

## Внешние источники

Данные о клиенте собираются из четырёх источников и сохраняются в заявке как проверки (`checks`):

| Источник | Откуда | Статус `fail` (стоп-фактор) | Статус `warning` (нужно внимание) |
|---|---|---|---|
| `bank` | внутренние данные банка: обороты по счёту | — | оборотов меньше 6 месяцев; падение оборотов на 30% и больше |
| `egrul` | ЕГРЮЛ / ЕГРИП | не найден; ликвидирован, ликвидируется, банкрот | реорганизация; бизнесу меньше 6 месяцев |
| `nbki` | бюро кредитных историй | текущая просрочка; просрочки 90+ дней за 24 мес. | просрочки 30–89 дней; 5+ запросов истории за 30 дней; истории нет |
| `pb` | ФНС «Прозрачный бизнес» | дисквалифицированные лица в управлении | массовый адрес или руководитель, недостоверные сведения, долг по налогам, нет отчётности |

Если источник не ответил, проверка получает статус `unavailable` — остальные данные сохраняются.
Правила — функции `*_check` в `app/services/enrichment.py`: простые, без сети и базы, покрыты тестами.

**Данные источника (`details`)** видит только аналитик. Формат — строгие модели из `app/schemas/checks.py`
(в OpenAPI — `BankDetails`, `RegistryDetails`, `CreditHistoryDetails`, `RiskDetails`, `UnavailableDetails`),
выбирается по `source`, а при `status = unavailable` — всегда `UnavailableDetails`. `null` — данных нет
(демо-заявка, проверки ещё не обновлялись).

Причина недоступности (`details.reason`) — закрытый список, подписи для интерфейса — в `GET /api/dictionaries`
(`unavailableReasons`):

| `reason` | Когда | Повторы |
|---|---|---|
| `timeout` | источник не ответил за `INTEGRATION_TIMEOUT_SECONDS` | да |
| `connection_error` | не удалось подключиться | да |
| `server_error` | 5xx или 429, код — в `details.httpStatus` | да |
| `request_rejected` | 4xx: неверный ключ, формат, нет согласия; код — в `details.httpStatus` | нет |
| `invalid_response` | ответ в неожиданном формате | нет |

Как устроен вызов (`app/integrations/`):

- **Адаптер на каждый источник** (`egr.py`, `nbki.py`, `pb.py`) переводит «чужой» формат во внутренний.
  Из ответа читаются только нужные поля: новое поле у источника ничего не сломает. Неожиданный формат —
  это недоступность источника (`invalid_response`), а не ошибка 500 у нас.
- **Таймаут** `INTEGRATION_TIMEOUT_SECONDS` на попытку, подключение — не дольше 1 секунды.
- **Повторы** `INTEGRATION_RETRIES` с растущей паузой (0,5 → 1 → 2 с) — только для того, что может пройти
  со второй попытки: таймаут, обрыв связи, 5xx, 429. Ошибки 4xx не повторяются.
- **Трассировка:** все попытки одного запроса идут с одним `X-Request-Id` — он есть в логах бэкенда
  и в журнале симулятора (`GET /admin/requests`).
- **Параллельность:** ЕГРЮЛ, НБКИ и «Прозрачный бизнес» опрашиваются одновременно — время равно
  самому медленному источнику, а не сумме.
- **Транзакция не держится во время сетевых запросов:** данные для запросов читаются, транзакция закрывается,
  после ответов заявка читается заново. Если её за это время изменили — `409 concurrent_update`.
- **Согласие на запрос в БКИ** берётся из заявки (дано при подаче); бюро без согласия не ответит.

Переход на настоящие сервисы — смена адресов (`EGR_BASE_URL`, `NBKI_BASE_URL`, `PB_BASE_URL`) и ключа
(`INTEGRATION_API_KEY`) и, при отличии формата, правка одного адаптера. Остальной код с форматами источников не знаком.

Сейчас обогащение запускает специалист: `POST /api/analyst/applications/{id}/checks/refresh`
(статусы `enrichment`, `scoring`, `manual_review`, `docs_requested`; статус заявки не меняется).
Действие записывается в историю заявки событием `kind = checks_refreshed` с перечнем источников,
которые не ответили. На этапе 4 тот же код будет вызывать конвейер.

### История заявки

Каждое событие истории (`history[]`, таблица `application_events`) имеет вид `kind`:

| `kind` | Что произошло | `status` события |
|---|---|---|
| `status_changed` | заявка перешла в новый статус — только через `transition()` в `state_machine.py` | новый статус |
| `checks_refreshed` | данные из источников запрошены повторно — через `record_event()` | текущий статус, не меняется |

Новые виды событий добавляются в `EventKind` (и миграцией — в CHECK-ограничение колонки `kind`).

Показать отказоустойчивость на демо:

1. Swagger симулятора → `PUT /admin/sources/nbki` с телом `{"mode": "error"}`.
2. Swagger API, вход `analyst` → `POST /api/analyst/applications/A-1026/checks/refresh` —
   проверка НБКИ `unavailable`, остальные обновились; в логах `docker compose logs api` — три попытки с одним `request_id`.
3. `POST /admin/reset` в симуляторе → повторить шаг 2 — все проверки `ok`.

## База данных и миграции

Схема описана моделями в `app/db/models.py`, изменения схемы — миграциями Alembic в `migrations/versions/`.

```bash
uv run alembic current                                   # текущая версия схемы в базе
uv run alembic revision --autogenerate -m "Описание"     # создать миграцию по изменениям моделей
uv run alembic upgrade head                              # применить
uv run alembic downgrade -1                              # откатить последнюю
uv run alembic check                                     # есть ли изменения моделей без миграции
```

Правила:

1. **Схема меняется только миграцией.** Изменили модель — создайте миграцию в том же коммите.
   Тест `test_migrations_match_models` упадёт, если миграцию забыли.
2. **Автогенерацию проверяйте глазами.** Alembic не видит отдельные последовательности (`Sequence`),
   переименования (видит как «удалить + создать») и изменения значений по умолчанию на стороне базы.
3. **Применённые миграции не редактируются.** Если миграция уже в `main`, исправление — новая миграция.
4. **`downgrade` пишется всегда** и проверяется: `upgrade head → downgrade -1 → upgrade head`.

Особенности схемы:

- суммы — целые рубли (`BIGINT`), ставки — `NUMERIC(5,2)`;
- перечисления — строки с CHECK-ограничением (новое значение enum требует миграции);
- `applications.version` — оптимистичная блокировка: параллельное изменение заявки даёт `409 concurrent_update`;
- номера заявок — последовательность `application_number_seq` (`A-1000`, `A-1001`, …).

## Сиды (начальные и демо-данные)

JSON-файлы в `data/seed/` (в корне репозитория), формат строго проверяется моделями в `app/db/seed.py`:
опечатка в ключе или неверная контрольная сумма ИНН — ошибка загрузки, а не «тихо битые» данные.

| Файл | Содержимое |
|---|---|
| `products.json` | кредитные продукты |
| `companies.json` | компании-клиенты с реквизитами и банковским профилем (выручка, история обслуживания) |
| `accounts.json` | тестовые учётные записи |
| `demo_applications.json` | демо-заявки в разных статусах; время задаётся относительно момента загрузки |

В Docker папка подключается в контейнеры только для чтения (`./data/seed:/app/data/seed:ro`), путь задаёт `SEED_DIR`.

|---|---|---|
| `DATABASE_URL` | `postgresql+psycopg://credit:credit@localhost:5432/credit` | адрес базы (в Docker собирается из `POSTGRES_*`) |

| `DB_POOL_SIZE`, `DB_MAX_OVERFLOW` | `5`, `10` | размер пула соединений |
| `DB_ECHO` | `false` | печатать SQL-запросы в лог (отладка) |
| `EGR_BASE_URL`, `NBKI_BASE_URL`, `PB_BASE_URL` | `http://localhost:8001/egr` и т. д. | адреса внешних источников (в Docker — сервис `mocks`) |

| `INTEGRATION_RETRIES` | `2` | число повторов после неудачной попытки |
| `INTEGRATION_BACKOFF_SECONDS` | `0.5` | пауза перед первым повтором (дальше — вдвое больше) |
| `TEST_DATABASE_URL` | `…/credit_test` | база для тестов |

## Структура

```
app/
├── main.py           # создание приложения, подключение роутеров
├── config.py         # настройки из переменных окружения
├── errors.py         # единый формат ошибок
├── security.py       # JWT и проверка ролей
├── schemas/          # модели запросов и ответов (контракт API)
├── db/               # модели таблиц, подключение к базе, загрузка сидов
├── integrations/     # адаптеры внешних источников: ЕГРЮЛ/ЕГРИП, НБКИ, «Прозрачный бизнес»
├── services/         # бизнес-логика: заявки, автомат статусов, обогащение, решения аналитика, расчёты
└── api/routes/       # эндпоинты: принимают запрос, вызывают сервис, возвращают ответ
migrations/           # миграции Alembic
tests/                # тесты (pytest)
scripts/              # служебные скрипты (экспорт OpenAPI)
```

## OpenAPI

После изменения эндпоинтов или схем обновите спецификацию и закоммитьте её вместе с кодом:

```bash
uv run python scripts/export_openapi.py        # → docs/api/openapi.json
```

Забытую выгрузку поймает тест `test_openapi_file_is_up_to_date`. Коды ошибок 409 перечислены в описании
каждого эндпоинта; их полный список с пояснениями — `CONFLICT_CODES` в `app/errors.py`
(новый код без описания не пройдёт тест `test_conflict_codes_are_documented`).

## Зависимости

Версии зафиксированы в `uv.lock`. Добавить пакет: `uv add <пакет>` (для разработки — `uv add --dev <пакет>`).
Lock-файл коммитится вместе с `pyproject.toml`. Новую библиотеку добавьте в `THIRD_PARTY_NOTICES.md`.
