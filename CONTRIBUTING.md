# Правила совместной работы

Документ описывает, как команда работает с репозиторием `smart-credit-lk`: ветки, коммиты, Pull Request и синхронизация с `main`.
Если что-то непонятно или пошло не так — сначала `git status`, потом вопрос в чат команды. Не удаляйте и не перезаписывайте то, в чём не уверены.

---

## 1. Главные принципы

1. **`main` на GitHub — единственный источник правды.** В нём всегда рабочий код.
2. **В `main` напрямую никто не пушит и локально в нём не коммитит** (включая владельца репозитория). Ветка защищена правилом `protect-main`.
3. **Одна задача — одна короткая ветка — один Pull Request.** Ветка живёт от нескольких часов до 1–2 дней.
4. **В `main` код попадает только через Pull Request** способом *Squash and merge*.
5. **После мержа ветка «мертва»** — новую задачу начинаем в новой ветке от свежего `main`.
6. **Пушим часто**, минимум в конце каждого рабочего дня. Push в свою ветку не влияет на `main` и работу других.

## Шпаргалка

Короткая версия разделов 5–7. Команды — для Git Bash или терминала VS Code.

| Ситуация | Команды |
|---|---|
| **Начинаю новую задачу** | `git switch main` → `git pull` → `git switch -c <тип>/<область>-<задача>` |
| **Сохраняю работу** | `git status` → `git add <файлы>` → `git commit -m "<тип>(<область>): добавление …"` |
| **Первый push ветки** | `git push -u origin <ветка>` → создать PR (заголовок в формате коммита!) |
| **Последующие push** | `git push` — PR обновится сам |
| **Нужен свежий `main` в моей ветке** | `git fetch origin` → `git merge origin/main` → `git push` |
| **Нажали Update branch в PR** | `git pull` в своей ветке |
| **Конфликт** | решить в VS Code → `git add <файл>` → `git commit` → `git push` (отмена: `git merge --abort`) |
| **Мой PR влит (Merged)** | `git switch main` → `git pull` → `git branch -D <ветка>` |
| **Ревьюю чужой PR локально** | `git fetch origin` → `git switch <ветка>` → (`git pull`) → проверить → `git switch main` |
| **Не понимаю, где я** | `git status` и `git log --oneline --graph --all -15` |

Три правила, которые предотвращают почти все проблемы:
1. **Новая ветка — только от свежего `main`** (`git switch main` + `git pull` перед `git switch -c`).
2. **В `main` не коммитим.** Перед коммитом смотрим в `git status`, на какой мы ветке.
3. **После мержа ветку не продолжаем** — удаляем и начинаем новую.

## 3. Названия веток

Формат: `<тип>/<область>-<кратко-о-задаче>`

- **только латиница, цифры и дефисы**, в нижнем регистре, без пробелов и кириллицы;
- 2–5 слов, по смыслу задачи.

| Тип | Когда использовать |
|---|---|
| `feature/` | новая функциональность |
| `fix/` | исправление ошибки |
| `docs/` | документация, README, диаграммы, тест-сценарии |
| `chore/` | инфраструктура: Docker, конфиги, зависимости, CI |
| `refactor/` | переработка кода без изменения поведения |
| `test/` | только тесты |

Примеры:
```
feature/backend-application-api
feature/front-product-picker
fix/front-wizard-autosave
docs/state-diagram
chore/docker-compose-postgres
```

## 4. Сообщения коммитов

Формат (по мотивам Conventional Commits):
```
<тип>(<область>): <описание на русском>
```

- **тип и область — на английском** (их понимают инструменты и их проще фильтровать);
- **описание — на русском**, с маленькой буквы, без точки в конце;
- **описание начинается с отглагольного существительного**, которое называет действие: «добавление», «исправление», «обновление», «удаление», «перенос», «настройка», «описание»; дальше — объект в родительном падеже («добавление **эндпоинта**», «исправление **расчёта**»);
- длина первой строки — до ~72 символов;
- один коммит — одно логическое изменение.

Частые слова для начала описания:

| Слово | Когда |
|---|---|
| добавление | новый код, файл, экран, эндпоинт |
| исправление | ошибка, некорректное поведение |
| обновление | изменение существующего: текстов, версий, данных |
| удаление | убрали код, файл, зависимость |
| переработка | рефакторинг без изменения поведения |
| настройка | конфиги, Docker, окружение |
| описание | документация, комментарии, диаграммы |

| Тип | Значение |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `docs` | документация |
| `style` | вёрстка, стили, форматирование (без изменения логики) |
| `refactor` | переработка кода без изменения поведения |
| `test` | тесты |
| `chore` | инфраструктура, конфиги, зависимости |

Области: `backend`, `frontend`, `mocks`, `scoring`, `pipeline`, `data`, `docker`, `docs`.

Примеры:
```
feat(backend): добавление эндпоинта создания черновика заявки
feat(frontend): добавление экрана подбора кредитного продукта
fix(frontend): исправление автосохранения анкеты при переходе по шагам
feat(scoring): добавление балльной модели и матрицы решений
chore(docker): настройка сервиса postgres в docker-compose
docs: описание сценария проверки в README
docs: добавление правил совместной работы
```

Плохие примеры: `fix`, `правки`, `ещё раз`, `upd`, `asdf`, `добавил экран` (глагол вместо существительного), `экран подбора` (непонятно, что с ним сделали).

Если нужно пояснение — добавьте тело коммита (пустая строка после заголовка), его можно писать обычными предложениями:
```bash
git commit -m "fix(backend): исправление расчёта лимита" -m "Лимит считался от месячной выручки вместо годовой."
```

> Коммиты с русским текстом пишите в **Git Bash** или терминале VS Code — в старой консоли `cmd` возможны проблемы с кодировкой.

## 5. Pull Request

**Когда создавать:** после первого `git push` ветки — либо сразу как **Draft** (задача на день и дольше), либо в конце, когда всё готово.

**Как создавать:**
1. Открыть ссылку, которую Git выводит после первого push, или нажать **Compare & pull request** на странице репозитория (или *Pull requests → New pull request*).
2. Проверить ветки: `base: main ← compare: <ваша ветка>`.
3. **Заголовок** — в формате коммита, по-русски: `feat(frontend): добавление мастера подачи заявки`. При squash-мерже он станет коммитом в `main`.
4. **Описание** — по шаблону: что сделано, как проверить, `Closes #N` (если есть задача на доске).
5. **Reviewers** — кому показать; **Assignees** — себя.
6. **Create pull request** или **Create draft pull request**.

**Как обновлять:** просто продолжайте коммитить и пушить в ту же ветку — PR обновится сам. Новый PR после исправлений не создаём.

**Состояния:** *Draft* — работа идёт; *Open* — готов к ревью; *Merged* — влит, ветка закончена; *Closed* — закрыт без мержа.

**Хороший PR:** небольшой (в идеале до ~400 строк изменений), про одну задачу, без посторонних файлов, проект собирается.

## 6. Алгоритмы

### 6.1. Разовая настройка Git (каждому)
```bash
git config --global user.name "<ник на GitHub>"
git config --global user.email "<почта из GitHub>"
git config --global init.defaultBranch main
git config --global pull.rebase false
git config --global fetch.prune true
git config --global core.quotepath false   # нормальное отображение кириллицы в путях
```

### 6.2. Начать новую задачу
```bash
git switch main
git pull
git switch -c feature/<область>-<задача>
```

### 6.3. Во время работы
```bash
git status
git add <файлы>                          # конкретные файлы, а не всё подряд
git commit -m "feat(<область>): добавление <чего>"
git push -u origin feature/<...>         # первый раз
git push                                 # в дальнейшем
```
После первого push — создать PR (Draft или обычный, см. раздел 5).

### 6.4. Подтянуть свежий `main` в свою ветку
Делает **автор ветки**, когда нужен чужой код из `main`, ветка живёт дольше дня или перед отправкой PR на ревью.
```bash
# изменения в ветке должны быть закоммичены
git fetch origin
git merge origin/main
git push
```
Короткая запись первых двух команд: `git pull origin main`.
Альтернатива — кнопка **Update branch** в PR, после неё у себя: `git pull`.

### 6.5. Завершить задачу (после того как PR получил статус Merged)
```bash
git switch main
git pull
git branch -D feature/<...>
```
`-D` удаляет ветку и при squash-мерже обязателен. Удаляйте **только после** фиолетовой плашки *Merged*.

`git fetch --prune` отдельно писать не нужно: при настройке `fetch.prune true` (раздел 6.1) `git pull` сам убирает ссылки `origin/<ветка>` на ветки, удалённые на GitHub.
Локальную ветку prune не трогает — поэтому `git branch -D` всё равно нужен.

### 6.6. Ревью и мерж (ревьюер)
1. **Files changed** — просмотреть изменения, оставить комментарии.
2. При необходимости запустить у себя:
   ```bash
   git fetch origin
   git switch feature/<...>
   git pull                  # если смотрели ветку раньше
   # проверить
   git switch main
   ```
3. **Review changes → Approve** или **Request changes** с пояснением.
4. Если ветка отстала от `main` — **Update branch**. Если есть конфликты — их решает автор.
5. **Squash and merge** → проверить заголовок коммита → **Confirm**.
6. Написать в чат: «Влил #N (<что>), обновите `main`».

Свои PR владелец репозитория вливает сам; изменения общих файлов и API — после того, как их посмотрел затронутый участник.

**Автору PR:** отвечайте на комментарии, исправления пушьте в ту же ветку, по каждому замечанию — ответ или **Resolve conversation**.

## 7. Конфликты

Возникают, когда двое изменили одни и те же строки. Решает **автор ветки**.
```bash
git fetch origin
git merge origin/main        # Git сообщит CONFLICT и перечислит файлы
git status                   # файлы в состоянии "both modified"
```
1. Открыть файл в VS Code, выбрать **Accept Current / Accept Incoming / Accept Both** или поправить вручную.
2. Убедиться, что не осталось маркеров `<<<<<<<`, `=======`, `>>>>>>>`.
3. Завершить:
   ```bash
   git add <файл>
   git commit
   git push
   ```
Передумали посреди слияния — `git merge --abort`. Конфликт задевает чужой код — созвон на 5 минут.

## 8. Что нельзя коммитить

- `.env` и любые пароли, токены, ключи — только `.env.example` с безопасными значениями;
- `node_modules/`, `dist/`, `.venv/`, кэши, логи;
- реальные персональные данные — **все данные в проекте синтетические**;
- большие бинарные файлы без необходимости.

**Всегда коммитим** lock-файлы: `uv.lock`, `package-lock.json`.
Добавили стороннюю библиотеку, шрифт или ресурс — добавьте строку в `THIRD_PARTY_NOTICES.md`.

## 9. Если что-то пошло не так

**Закоммитил в локальный `main`** (push отклонён правилом):
```bash
git switch -c feature/<задача>        # коммиты переезжают в новую ветку
git push -u origin feature/<задача>
git switch main
git reset --hard origin/main          # вернуть main к состоянию GitHub
```

**PR пишет «Can't automatically merge» / ветка создана от старого `main`:** подтянуть `main` в свою ветку и решить конфликт (раздел 7):
```bash
git fetch origin
git merge origin/main
```

**GitHub подставил заголовок PR из имени ветки** (`Docs/contributing`) — так бывает, когда в ветке больше одного коммита. Нажать **Edit** рядом с заголовком PR и привести его к формату коммита.

**Нужно переключить ветку, а изменения не закоммичены:**
```bash
git stash          # спрятать
git switch <ветка>
# ...
git switch <исходная ветка>
git stash pop      # вернуть
```

**Push отклонён (`rejected … fetch first`):** на GitHub в вашей ветке есть коммиты, которых нет у вас (часто после *Update branch*):
```bash
git pull
git push
```

**Ошибка в сообщении последнего коммита, ещё не запушенного:**
```bash
git commit --amend -m "fix(frontend): исправление описания"
```
Если коммит уже запушен — не исправляйте, при squash-мерже итоговый заголовок задаётся отдельно.

**Не понимаю, что происходит:**
```bash
git status
git log --oneline --graph --all -15
```

## 10. Фиксация версии для сдачи

Выполняет владелец репозитория после последнего мержа:
```bash
git switch main
git pull
git tag -a v1.0.0 -m "Версия для сдачи"
git push origin v1.0.0
git rev-parse v1.0.0^{commit}    # commit hash для формы сдачи
```
